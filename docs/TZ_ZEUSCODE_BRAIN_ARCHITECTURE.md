## 1. Продукт ZeusCode — суть одной картиной

### 1.1 Одной фразой

ZeusCode — **мозг + биллинг** для кодинга: один ключ, один адрес API, режимы силы.  
Клиент (Cursor / Cline / OpenCode / Goose / …) — **руки** (файлы, терминал, git, LSP).

### 1.2 Что человек получает

| Слой | Ответственность |
|------|-----------------|
| **Клиент** | Редактирует файлы, запускает shell, показывает UI |
| **Zeus `/v1`** | Роутит задачу, зовёт 1…N моделей, синтезирует ответ, списывает ₽ |
| **Режимы (TG «Модели»)** | Пользовательский / Продвинутый / Набор — *не* отдельные model id в клиенте |
| **Клиентский model id** | Почти всегда `zeuscode` (или соло-id из каталога) |

### 1.3 Что ZeusCode **не** делает (границы)

- Не свой IDE и не порт agent-loop с omp/Cursor на сервер.  
- Не marketplace на 400 моделей.  
- Не RAG по всему репо пользователя на сервере (MVP).  
- Studio / `orchestrate` на сайте — deprecated; один умный путь: **ZeusCode `/v1`**.

### 1.4 Суть разработки (зачем строим «связку»)

Проблема рынка: одна модель то сильна, то слепа; человек сам гадает «кого включить сегодня».  
Гипотеза ZeusCode: **составной мозг** (роутер + 1…N специалистов + проверка) даёт лучше соотношение **сила / цена / надёжность**, чем одна случайная модель — *если* связка не превращается в шум.

**Критерий успеха продукта:** в клиенте пользователь пишет задачу → получает рабочий код/ответ → платит прозрачно → не думает о зоопарке провайдеров.

## 2. История попыток (контекст решений)

Зафиксировать как **факт продукта**, чтобы не повторять ошибки:

| Этап | Что делали | Наблюдение |
|------|------------|------------|
| **A. Три нейронки** | Панель ~3 моделей (роли / diversity) | «В принципе что-то получилось» — управляемо, понятно |
| **B. Пять «каждая за свою задачу»** | Больше ролей / веток на запрос | Рост сложности пайплайна, координация, биллинг |
| **C. Пять без жёсткого cap** | Больше параллели / судей / аспектов | **«Каша»**: шум, конфликты, дороже, хуже предсказуемость |

**Рабочий вывод (гипотеза для ТЗ):**  
«Больше нейронок» ≠ «лучше». Выигрыш даёт **правильная топология** (кто когда вызывается), а не размер панели.  
Нужен **жёсткий cap** и явные роли, иначе система снова скатывается в кашу.

## 3. Исследования — что прикреплено и как читать

### 3.1 Draco / fusion panel (research-bench, интернет-задачи)

Источник: исследование связок моделей на бенче **Draco** (оценка качества ответов на research/web-style задачах; в артефактах — `world-bench/draco`, ladder charts в `bench-power/`).

**Картина (ladder / fusion panel, scored on 93 of 100 tasks — ориентир по приложенному графику):**

| Конфигурация | Тип | Ориентир score |
|--------------|-----|----------------|
| Fable 5 + GPT-5.5 | fusion (2) | ~69% (топ) |
| Opus 4.8 + GPT-5.5 + Gemini 3.1 Pro | fusion (3) | ~68.5% |
| Opus 4.8 + GPT-5.5 | fusion (2) | ~67.5% |
| Opus 4.8 + Opus 4.8 (self-fusion) | fusion (2) | ~65.5% |
| Claude Fable 5 | solo | ~65.3% |
| Gemini 3 Flash + Kimi K2.6 + DeepSeek V4 Pro | fusion (3 light) | ~64.8% |
| DeepSeek V4 Pro / GPT-5.5 / Opus 4.8 | solo | ~59–60% |
| Kimi / Gemini 3.1 Pro / Gemini 3 Flash | solo | ниже |

**Что из этого следует (для архитектуры):**

1. **Fusion часто бьёт solo** той же семьи — связка имеет смысл.  
2. **Топ — 2 модели**, не 5. Тройка почти рядом, но не «магически лучше».  
3. **Self-fusion** (одна модель дважды в разных ролях) уже лучше solo — важен **протокол** (verify / debate), не обязательно «пять разных брендов».  
4. Fusion из **трёх слабых** может проигрывать **одному сильному solo** — состав панели критичен.  
5. Это бенч **research / критерии Draco**, а не LiveCodeBench / SWE-bench / Terminal-Bench.

### 3.2 Чего Draco **не** доказывает

| Утверждение | Статус |
|-------------|--------|
| «Лучшая связка на Draco = лучший coding agent» | **Не доказано** — другой навык |
| «Нужно всегда 2 модели» | Гипотеза; зависит от задачи (чат vs agent tools) |
| «5 моделей всегда хуже» | Наблюдение продукта («каша»), не прямой score с графика |
| «Fable обязателен в Zeus» | Нужна проверка: доступность upstream, tools, цена, coding benches |

### 3.3 Другие бенчи — обязательный слой для кодера

Чтобы ответить «насколько эти нейронки хороши **в коде**», ТЗ требует **отдельной матрицы**, не экстраполяции с Draco:

| Бенч / класс | Что меряет | Зачем ZeusCode |
|--------------|------------|----------------|
| **LiveCodeBench** (или аналог) | Алгоритмы / competitive coding | «Умеет писать правильный код» |
| **SWE-bench (Lite/Verified)** | Патчи в реальных репо | Agent + tools + edit |
| **Terminal-Bench / TB** | Shell / CLI agent loop | «Руки клиента + мозг Zeus» |
| **Внутренний human matrix** (`CLIENTS-TEST-LIST`) | Клиенты × tools × файлы × режимы | Продуктовая правда |
| **Draco / research** | Синтез / исследование | Режим «думает / ищет / сравнивает» |

**Правило ТЗ:** решение о составе панели принимается только если есть **оба**:

- score (или ранг) на **research-like** (Draco / ladder);  
- score (или ранг) на **≥1 coding / agent** бенче + lab checklist клиентов.

Один столбец без второго = **недостаточно** для продуктового выбора.

### 3.4 Связь с текущим Zeus (brownfield)

Уже есть в коде / docs:

- режимы `simple` / `power` / `custom`;  
- пути FAST / CASCADE / RACE / FULL (каркас);  
- роли doer / leader / verifier / judge (см. role-routing ТЗ);  
- auto-роутинг **1 ↔ 3**, не auto-2 (историческое правило — **пересмотреть** в свете Draco: 2-model fusion часто топ);  
- lab: клиенты OpenCode / Codex / Cline / Continue / Claude / Aider / Goose.

ТЗ требует явно решить: оставить «никогда auto-2» или разрешить **DUAL** как first-class path (см. §5).

## 4. Проблема, которую решаем (problem statement)

### 4.1 Симптом

При росте числа одновременных LLM на один запрос:

- ответы конфликтуют или «усредняются» в посредственность;  
- растёт latency и ₽;  
- сложно объяснить пользователю «кто что сделал»;  
- tools/agent path ломается или упрощается до соло без ролей;  
- сложно тестировать и откатывать.

### 4.2 Корневой вопрос (единый)

> Как собрать **единую систему**, где число нейронок, их роли и момент вызова **однозначно определены** задачей — так, чтобы не возвращаться к «каше из пяти», но и не упускать выигрыш fusion с Draco?

### 4.3 Подвопросы (не упустить)

1. **Сколько** нейронок на один пользовательский запрос (cap hard / soft)?  
2. **Какие** модели в пуле simple / power / custom?  
3. **Роли:** кто leader, doer, verifier, judge — обязательные vs опциональные?  
4. **Когда** 1, когда 2, когда 3 (и нужен ли когда-либо 4–5)?  
5. **Где** живёт логика: только Zeus server vs клиентский agent loop?  
6. Как **не смешивать** research-панель и coding-панель (разные default stacks)?  
7. Как **мерить** успех: Draco ≠ coding; нужны coding benches + client matrix.  
8. Как **биллить** честно при multi-call?  
9. Как **деградировать** при 502 upstream (уже видно на lab: opus/kie flake)?  
10. Как **объяснить** пользователю режим без жаргона «fusion panel»?

## 5. Целевая архитектура (требования к решению)

### 5.1 Инварианты (обязательно сохранить)

| ID | Инвариант |
|----|-----------|
| I1 | Zeus = мозг + billing; клиент = руки |
| I2 | Публичный id `zeuscode` стабилен |
| I3 | Режим силы — prefs аккаунта / TG, не зоопарк id в клиенте |
| I4 | Не стрипать tools без замены на осмысленный agent path |
| I5 | Не слать ×N полный Cursor-контекст всем веткам (голова full, сателлиты brief) |
| I6 | Early-exit только через verifier / policy, не «модель сама сказала что она права» |
| I7 | Hard cap на число **одновременных LLM-ролей** на запрос (см. 5.2) |

### 5.2 Cap: сколько нейронок

**Требование (MUST):** зафиксировать жёсткий потолок:

| Класс запроса | Max LLM-вызовов «делателей» | Verifier / judge |
|---------------|----------------------------|------------------|
| Light / chat / мелочь | **1** | optional mini (0–1) |
| Normal coding | **1–2** | mini 0–1 |
| Hard / FULL | **≤3** doers | judge отдельно, **не** считается 4-м doer в UI для юзера, но **учитывается в billing** |
| Запрещено по умолчанию | **≥4 doers** на один turn | Только experiment flag |

**Следствие из Draco + продукта:** default «лучшие» конфигурации искать в зоне **2 или 3**, не 5.  
Пять — только как **пул на выбор** (catalog / custom), не как «все пятеро всегда в одном запросе».

### 5.3 Топологии (куда ставить)

Система должна явно поддерживать пути (имена можно сохранить из roadmap):

```text
FAST      → 1 doer (+ optional cheap failover)
DUAL      → 2 модели (leader + peer ИЛИ doer + verifier)  ← приоритет исследования
CASCADE   → cheap → verify → escalate to stronger
RACE      → 2 параллельно, первый годный, cancel второй
FULL      → ≤3 doers + structured judge (не клон панели)
```

**Решение, которое ТЗ требует принять (выход арх. спринта):**

- [ ] Разрешить **DUAL** как auto-path (пересмотр «никогда auto-2»).  
- [ ] Зафиксировать: FULL = **3 doers max**, не 5.  
- [ ] Custom mode: пользователь выбирает **до 3** в панели (уже в UX); сервер **режет** >3.

### 5.4 Роли — за что отвечают

Минимальный набор ролей (MUST иметь чёткую семантику в коде и логах):

| Роль | За что отвечает | Когда |
|------|-----------------|-------|
| **Router / classifier** | Фаза, сложность, путь, effort | Всегда (дешёвый / regex fallback) |
| **Leader / doer_primary** | Основной ответ или патч | Почти всегда |
| **Peer doer** | Альтернатива / другой аспект (UI vs logic) | DUAL / FULL |
| **Mini-verifier** | «Достаточно ли?» escalate / early-exit | CASCADE / soft-stop |
| **Judge** | Слияние / выбор ветки | FULL / conflict |
| **Disaster failover** | Пустой/битый ответ → другая модель | Ошибки upstream |

**Запрещено:** плодить роли «на всякий случай» без бенч-доказательства пользы.

### 5.5 Два стека моделей (research vs code)

**MUST развести конфиги:**

| Стек | Оптимизация | Пример кандидатов (не финальный выбор) |
|------|-------------|----------------------------------------|
| **Research / think** | Draco-like, синтез, сравнение | Fable+GPT-5.5; Opus+GPT-5.5±Gemini |
| **Coding / agent** | tools, patch, shell, SWE/LCB | Opus / DeepSeek-V4-Pro / Gemini-Pro / GPT — **по coding benches** |

Режимы пользователя:

- **Пользовательский (simple)** — дешевле, coding-lean, 1–2 вызова.  
- **Продвинутый (power)** — coding stack сильнее; research stack только если task_kind = research/compare.  
- **Набор (custom)** — до 3 id из каталога; сервер не раздувает до 5.

### 5.6 Реализация (как собрать в единую систему)

Обязательные компоненты (уже частично есть — довести до инвариантов):

1. **Единый вход** `POST /v1/chat/completions` (+ Responses / Messages bridges для клиентов).  
2. **Policy layer:** classify → path → panel slice → timeouts.  
3. **Panel registry:** id модели → роль → max_tokens → adapter.  
4. **Execution:** parallel/cancel, soft-stop, disaster codes.  
5. **Verify gate:** mini / tests / logs (по role-routing ТЗ).  
6. **Billing:** каждая ветка + judge + classifier.  
7. **Observability:** `onestack` / trace: path, panel, tokens, ₽, disaster.  
8. **Eval harness:** Draco ladder + coding benches + client checklist — один dashboard «go / no-go» для смены панели.

### 5.7 Отказоустойчивость

- Upstream 502 (Kie и др.) ≠ «Zeus сломан»: failover + понятная ошибка клиенту.  
- Solo-reroute при `tools` (агенты) — не гнать fusion, который стрипает tools (уже урок lab).  
- Client-hands policy: модель не отказывается от «терминала пользователя».

## 6. Как решить «сколько и кого» — метод (обязательный процесс)

Не голосовать «на глаз». ТЗ задаёт **процедуру**:

### Шаг 1 — Зафиксировать гипотезы панели

Пример гипотез (заполнить цифрами после прогонов):

| ID | Гипотеза | Ожидание |
|----|----------|----------|
| H1 | DUAL (2 strong) ≥ FULL (3) на coding tasks при меньшей цене | latency↓ ₽↓ quality≈ |
| H2 | Power panel 3 doers лучше 5 на human agent matrix | меньше каши |
| H3 | Research stack ≠ coding stack | разные winners на Draco vs SWE/LCB |
| H4 | Self-fusion / verify даёт + без второй «дорогой» модели | дешевле |

### Шаг 2 — Прогнать одну матрицу на одних данных

Набор минимума:

1. Draco (или subset) — research.  
2. LiveCodeBench subset **или** внутренний coding suite.  
3. SWE-lite / 5–20 задач **или** Terminal pilot.  
4. Client checklist (хотя бы 1 CLI agent: write/edit/shell) на `zeuscode` + power/simple/custom.

### Шаг 3 — Decision table

| Метрика | Порог «берём в прод» |
|---------|----------------------|
| Research score vs baseline solo | не хуже −1pp без выигрыша ₽/latency |
| Coding / agent pass rate | ≥ baseline текущего power |
| Client checklist FAIL критичные (auth, write, tools) | **0** |
| Avg ₽ / успешный hard-запрос | ≤ текущего power + X% (задать X) |
| Каша (субъективно / conflict rate) | ↓ vs 5-model experiment |

### Шаг 4 — Выкат

Shadow → 10% → 50% → 100%, rollback по метрикам §6 шаг 3.

## 12. Резюме для решений (executive)

1. **ZeusCode** — составной coding brain + billing; клиент — руки.  
2. **3 модели** у вас уже давали пользу; **5 в одном запросе** дали кашу — фиксируем **cap ≤3 doers**.  
3. **Draco** показывает: лучшие связки часто **2–3**, не 5; fusion > solo; но это **research**, не код.  
4. Нужна **вторая ось измерения** — coding/agent benches — иначе нельзя честно выбрать панель для кодера.  
5. Архитектура = **пути (FAST/DUAL/CASCADE/FULL) + роли + два стека (research/code) + eval gate**, а не «накидать нейронок».  
6. Следующий шаг после утверждения ТЗ: заполнить §7 (D1–D10) и прогнать §6 (процедура выбора панели).

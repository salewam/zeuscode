## 0. Одна картина

ZeusCode — **мозг + биллинг**. Клиент (Cursor / Cline / OpenCode / Aider / Goose / Codex) — **руки**: файлы, терминал, git, LSP.

Человек видит **одну сильную модель**, которая с ним говорит. Под ней работает дешёвая бригада, где каждая роль закрывает чужую слепую зону.

**Несущий принцип экономии:** чем дороже роль, тем короче её вход и тем реже её зовут. Дорогая модель никогда не читает сырьё — только выжимки. Одиночная мощная модель дорога не из-за цены за токен, а потому что перечитывает весь контекст на каждом ходу.

**Несущий принцип надёжности:** решение «готово» опирается на машинные сигналы, а не на мнение модели.

**Границы.** Не свой IDE. Не marketplace на 400 моделей. Не порт agent-loop на сервер (клиент исполняет, Zeus управляет). Человек при этом не делает руками ничего.

## 1. Бригада — состав и ответственность

| Роль | Модель | За что отвечает | Что получает на вход |
|------|--------|-----------------|----------------------|
| **Ведущий (лицо)** | `claude-opus-4-6` *(временно; кандидат на замену — `claude-opus-4-8`: новее и дешевле)* | Говорит с человеком. Оценивает запрос, сложность, архитектуру. Распределяет работу. Разрешает спорное. Собирает финальный ответ | Только выжимки и артефакты. **Никогда — сырьё** |
| **Исследователь A** | `gemini-3-flash-preview` | Веб-исследование через `web_tools.py` | Запрос + результаты поиска |
| **Исследователь B** | `kimi-k2.6` | То же, другая школа | То же |
| **Исследователь C** | `deepseek-v4-pro` | То же, другая школа | То же |
| **Аналитик** | `deepseek-v4-pro` | Слияние трёх исследований в одну сводку **с пометками расхождений**. Чтение сырых логов, traceback, вывода тестов → `log_digest` | Сырьё в любом объёме |
| **Доер логики (код)** | `gpt-5.4` | Основной объём кода и патчей | Один шаг плана + список файлов + критерий готовности + содержимое этих файлов |
| **Доер UI (ведущий по дизайну)** | `claude-opus-4-6` | Вёрстка, компоненты, дизайн-решения | Бриф + эталоны из насмотренности |
| **Критик дизайна** | `gemini-3.1-pro` | Не создаёт. Находит слабые места, сравнивая с эталонами. Задаёт человеку вопрос про конкурентов | Скриншот + эталоны + бриф |
| **Автор тестов** | `gpt-5.3-codex-spark` | Тесты и объективные критерии проверки | Патч + критерий готовности |
| **Верификатор** | `claude-haiku-4-5` | Гейт: готово / доработать / поднять к ведущему. **Код не пишет никогда** | Машинные сигналы + `test_report` + `log_digest` |
| **Vision** | через `_pick_vision_model()` (`roles.py:499`) | Смотрит скриншот, говорит что сломано и что нажать. Проверяет **работает ли**, а не «красиво ли» | Скриншот |
| **Аварийный failover** | политика, не модель | Пустой/битый ответ → другой мерчант → другая модель | — |

**Правила состава:**
- Модель входит в бригаду только **выиграв конкретную роль на бенче**. На роль садится **одна** модель.
- Разные школы обязательны у исследователей и в паре «доер + критик»: модели одной школы ошибаются одинаково, и взаимная проверка становится бесполезной.
- Роль не плодится «на всякий случай» без бенч-доказательства пользы.

### 1.1 Слитые роли (было три — стало одна)

Диспетчер, судья и сборщик финального ответа **слиты в Ведущего** по модели: `architect` = `judge_fix` = куратор = `opus-4-8` (лицо временно `opus-4-6`). Отдельные LLM-вызовы judge/soft-stop пока остаются — полное слияние вызовов в один turn ещё не сделано.

### 1.2 Чёрный список — никогда не роутить

| Модель | Причина |
|--------|---------|
| `gpt-5.3-codex` | Выход ~$268/1M — дороже Fable 5 вчетверо |
| `gpt-4o` | ~$39.6/$158 при слабом результате |
| `gpt-5.6` | ~$20.7/$88.8 — дороже Opus без выигрыша |
| `claude-opus-4-7` | Дороже `opus-4-8` при том же классе |

## 2. Как собирается запрос (критично для кэша)

Кэш промпта работает **только при стабильном префиксе**. Поэтому блоки идут строго от самого редко меняющегося к самому свежему:

```text
1. Системный промпт роли              (константа)
2. Клиентский системный промпт        (append, НИКОГДА не replace)
3. Память проекта                     (меняется редко)
4. Эталоны / насмотренность           (для дизайн-задач)
5. Артефакты задачи: brief, plan      (меняются по шагам)
6. Сжатая история диалога             (компрессор)
7. Свежий запрос + свежие артефакты   (меняется каждый ход)
```

**Если свежие данные попадут выше пункта 7 — кэш не сработает никогда, и весь обвес окажется бесполезным.** Это архитектурное требование к сборке сообщений, а не флаг в запросе.

**Про клиентский системный промпт:** Zeus **дописывает, но не перезаписывает**. Если человек пришёл со своими скиллами (BMAD, свои правила Cursor, свой промпт) — бригада работает внутри его процесса, а не вместо него. Модель поведения — как в `client_hands.py` (`HANDS_SYSTEM_APPEND`).

## 3. Как идёт задача

### 3.1 Лестница, а не разовый выбор

Тяжёлая бригада собирается не «на серьёзный запрос», а на запрос, который **не закрылся** силами полегче.

```text
Ведущий читает запрос
  ├─ тривиально           → отвечает сам
  ├─ нужен факт из сети   → 3 исследователя → аналитик сливает → ведущий отвечает
  └─ нужна работа с кодом → план (шаги, файлы, критерий готовности)
        └─ по шагу: доер → патч
              → клиент применяет и прогоняет тесты (руки)
              → аналитик сворачивает вывод → log_digest / test_report
              → верификатор: машинные сигналы + отчёт
                   ├─ зелёно → следующий шаг
                   ├─ жёлто  → доработка тем же доером (≤ MAX_ESCALATE_GLOBAL)
                   └─ красно → поднять к Ведущему (он же судья)
```

**Асимметрия решений — обязательна:**
- Диспетчеризация (внутри Ведущего): при любом сомнении роутить **вверх**. Ошибка «недооценил» стоит один дешёвый вызов; ошибка «переоценил» — немного денег.
- Верификатор: сказать «доработать» дёшево, сказать «готово» — ответственно. Порог на «готово» высокий, при сомнении — эскалация.

### 3.2 Второй запрос в том же проекте

Не собирает бригаду заново. Память проекта и состояние сессии уже содержат план, карту файлов и решения — Ведущий видит, что мы внутри шага, и не поднимает тяжёлый путь повторно.

### 3.3 Контур UI-проверки

```text
браузерный демон открывает страницу
  → скриншот → vision: что сломано, что нажать
  → click-selector (browser_client.py уже умеет)
  → новый скриншот → сверка «изменилось ли то, что должно»
```

Проверяется **работает ли**: кнопка нажимается, форма отправляется, ошибка показывается. Это третий слой машинной правды после тестов и компиляции.

### 3.4 Насмотренность

При дизайн/продуктовой задаче критик **один раз** спрашивает: «есть примеры, на которые ориентируетесь?». Ответ уходит в память проекта — повторно человек этого вопроса не слышит.

Ссылки складываются в каталог по категориям (дашборды, лендинги, формы, онбординг) и работают дальше на других пользователей: если новый человек ничего не назвал, критик берёт эталоны из накопленного, а **не из поисковой выдачи**.

Обоснование: модель с поиском не способна отличить «топового» конкурента от того, кто хорошо сидит в SEO. Промптом это не лечится. Живой поиск — только чтобы подтянуть свежий скриншот эталона, но не чтобы решать, кто эталон.

Обратная связь «вот так хорошо» тоже пополняет каталог. Это актив, которого нет ни у кого: модели у всех одинаковые, насмотренность — нет.

## 4. Артефактная шина

Роли обмениваются **строго типизированными артефактами**, а не свободным текстом. Когда пять моделей переписываются прозой — получается шум; когда каждая читает и пишет фиксированную структуру — шума нет.

| Артефакт | Кто пишет | Кто читает |
|----------|-----------|------------|
| `research_digest` (с пометками расхождений) | Аналитик | Ведущий |
| `brief` (`brief.py` уже есть) | Ведущий | Доеры, критик |
| `plan` (шаги, файлы, критерий готовности) | Ведущий | Доеры, верификатор |
| `patch` | Доер | Клиент, автор тестов, верификатор |
| `log_digest` | Аналитик | Верификатор, Ведущий |
| `test_report` | Автор тестов + прогон клиента | Верификатор |
| `ui_report` (скриншот + что сломано) | Vision | Верификатор, доер UI |
| `verdict` | Верификатор | Ведущий |

**Правила:** артефакты версионируются; роль не имеет доступа к тому, что ей не адресовано; роль не перезаписывает чужой артефакт.

## 5. Обвесы

### 5.1 Экономия токенов
1. **Кэш промпта** со стабильным префиксом по §2. — **есть:** `prompt_assembly.py` в hot-path `_monolith`
2. **Учёт `cached_tokens`** в биллинге. — **есть:** `responses_compat` + `cost.estimate_*` + `metrics.cache_hit_pct`
3. **Контекстный компрессор** — **есть (детерминированный):** `context_compress.py` (без лишнего LLM-вызова)
4. **Дедупликация** — один и тот же вопрос в сессии не уходит в модель дважды. — **ещё нет**
5. **Brief-сателлиты** (`brief.py`) — дорогие роли никогда не получают полный контекст. — **было**

### 5.2 Надёжность
6. **Скоринг мерчантов** поверх A6 + кольцевой failover. — **частично:** failover в `policy.LEADER_FAILOVER`; скоринг мерчантов — в дашборде A6
7. **Два токена A6** — **не в коде:** руками в кабинете A6
8. **Пустое наружу не уходит** + за disaster не биллим. — **есть:** `_ensure_non_empty_completion` + `_is_disaster` → ₽0
9. **`empty_rate` — метрика №1.** — **есть:** `metrics.empty_rate` + alert stub

### 5.3 Правда вместо догадок
10. **Машинные сигналы на входе верификатора** — **есть:** `GateSignals` + `machine_signals_from_client(zeus.exec)`
11. **Артефактная шина с версиями** (§4). — **частично:** brief/plan есть; полный bus — дальше
12. **Трассировка** — **частично:** `observe_request` / branches; профиль токенов в snapshot

### 5.4 Глаза и руки
13. **Скриншот + vision** — **есть:** `browser_client.web_screenshot` / `ui_verify_loop` + `vision_ui.py`
14. **Курируемая насмотренность** (§3.4). — **есть:** `taste.py` + вопрос один раз через память

### 5.5 Самообучение
15. **Память проекта** — **есть:** `project_memory.py` (файл + in-process)
16. **Статистика ролей → автоподбор** — **ещё нет** (сигналы есть)
17. **Копилка ошибок** — **есть:** `error_bank.py`

### 5.6 Контроль
18. **Eval-гейт** — **ещё нет** как блокирующий CI-гейт перед сменой бригады
19. **Потолок панели = 3.** — **есть**

## 6. Что убирается из структуры

| Что | Почему | Статус |
|-----|--------|--------|
| **Путь ≥4 доеров на один turn** | Источник «каши из пяти». Потолок 3, пять — только меню каталога, не одновременный вызов | **убрано:** `FUSION_MAX_PANEL = 3`, зажат в `roles.py` и `_monolith.py` |
| **Классификация сложности по длине строки** | `len(q) <= 80 → chat`, `len(q) >= 900 → heavy`. «Перепиши auth на JWT» = 20 символов → `chat` | **убрано:** длина больше не влияет на сложность. Простоту определяет `_MICRO_EDIT_RE` (характер правки), тяжесть — `detect_second_signal`, глубину трейсбэка — число кадров |
| **Отдельные роли «диспетчер» и «судья»** | Слиты в Ведущего (§1.1) — меньше стыков | **частично:** модель одна (`architect` = `judge_fix` = `curator` = `opus-4-8`), но вызовы всё ещё раздельные — слияние вызовов не сделано |
| **Правило «никогда auto-2»** | Противоречит замерам Draco: двойка в топе. DUAL — полноправный путь | **убрано:** правило жило только в докстринге `_monolith.py`; в `first_match_policy` CASCADE (2) уже легален (`policy_light_cascade`, `policy_default_cascade`) |
| **Наложение прайса polza.ai на каталог A6** | Ложный себес: чужая ставка поверх нулевых цен A6 | **убрано:** `sync_polza_prices()` снят со старта. Вместо него `apply_measured_prices()` — замеренный по списаниям себес, **37 из 59** моделей. Остальным 22 замер испорчен (см. §7 H7) |
| **`cached_tokens: 0` хардкодом** | Ломает и учёт кэша, и экономику | **убрано:** читаем `prompt_tokens_details.cached_tokens` от апстрима |
| **Роутинг A6 «строго низкая цена, пул 30%»** | Прямая причина пустых ответов: у дешёвых мерчантов успешность падает до 43% | **не в коде:** настройка в дашборде A6, переключается руками |
| **Studio / `orchestrate`** | Один умный путь — ZeusCode `/v1` | **убрано:** `routers/studio_fs.py` и `routers/projects.py` удалены (в роутинг уже не подключались) |
| **`claude-opus-4-6` на архитекторе/судье** | `opus-4-8` новее и дешевле — замер подтвердил: $10.2/$51.1 против $13.8/$68.3 у 4-7 | **убрано:** `opus-4-8` на `architect`/`judge_fix` и в power-стеке |
| **Модели из чёрного списка** (§1.2) | Дороже топа без выигрыша | **убрано:** `catalog.ROUTING_BLACKLIST` → `ready=False`; в авто-пул не попадают, явный запрос даёт 400 |

## 8. Порядок работ

| Ступень | Что | Приёмка | Статус |
|---------|-----|---------|--------|
| **0** | Роутинг A6 на качество + два токена. Пустое не уходит, disaster не биллим, `empty_rate` | DRACO 100: пустых **< 1%** | **код готов** (empty/bill/metric); A6-роутинг — руками; DRACO не перегоняли |
| **1** | Потолок панели = 3. Id бригады по §1. Чёрный список | Нет пути ≥4 доеров | **готово** |
| **2** | Машинные сигналы в гейт | «Готово» не без машинного сигнала | **готово** (клиент шлёт `zeus.exec`) |
| **3** | Кэш + сборка §2 + учёт cache | cache_hit_pct в snapshot | **готово** |
| **4** | Скриншот + vision | Vision ловит нерабочую кнопку | **код готов**; нужен живой daemon |
| **5** | Память + насмотренность + копилка | Второй запрос дешевле | **код готов**; экономика 2-го запроса — замер позже |
| **6** | Телеметрия профиля токенов | Себес ±20% | **частично:** counters есть; отчёт по юзеру — дальше |
| **7** | Coding-бенчи → фиксация бригады | Бьёт соло-модель | **не начато** |

Обоснование порядка: ступень 0 определяет, работает система или врёт. Ступень 2 определяет, не врёт ли она про «готово». Кэш экономит, но экономить на неработающей системе нечего.

## 9. Критерии приёмки ТЗ

- [ ] `empty_rate` < 1%, пустой ответ физически не может дойти до клиента.
- [ ] На hard-задаче не более **3 доеров**; пути к ≥4 нет.
- [ ] «Готово» не выдаётся без машинного сигнала.
- [ ] Дорогие роли не получают сырьё — только выжимки (проверяемо по трассировке токенов).
- [ ] Кэш-хиты видны и учтены в биллинге.
- [ ] Клиентский системный промпт и скиллы человека не перезаписываются.
